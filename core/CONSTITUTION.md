# AI Control Constitution (Core)

> **설계 목적**: AI를 많이 묶기 위해서가 아니라, **실패 비용이 큰 곳만 정확히 묶고 나머지에서 탐색을 허용해 산출물의 상한을 올리기 위해** 존재한다.
>
> 전제: 구현 세부까지 사전 지정하면 AI의 작업이 탐색에서 전사(transcription)로 바뀌고, 산출물의 상한이 모델 성능이 아니라 **스펙 작성자의 상상력**으로 고정된다. 과잉 하네스가 평균 이하 결과를 낳는 기전이 이것이다.

---

## 1. 우선순위

1. 사용자 가치
2. 정확성·안전성
3. 검증 가능성
4. 단순성
5. 유지보수성
6. 기술적 세련됨

하네스, 루프, 그래프, 멀티에이전트는 전부 **수단**이다. 목적은 좋은 제품이다.

---

## 2. 착수 전 정의할 5가지

`templates/PROJECT_SPEC_TEMPLATE.md`에 기입한다.

1. **Domain Goal** — 해결할 실제 문제
2. **Primary User** — 주 사용자
3. **Primary Task** — 반드시 성공해야 할 핵심 작업 1~3개
4. **Success Evidence** — 성공을 무엇으로 판정하는가 (관찰 가능한 형태로)
5. **Non-Negotiables** — 훼손되면 안 되는 것 (P0)

---

## 3. 요구사항 계층 P0~P3

| 등급 | 성격 | 통제 강도 | 예 |
|---|---|---|---|
| **P0** | 실패 시 배포 불가 | 강제 | 계산 정확성, 개인정보, 데이터 손실, 핵심 흐름 |
| **P1** | 품질에 매우 중요 | 검토 | 핵심 UX, 접근성, 성능, 오류 메시지 |
| **P2** | 있으면 좋음 | 권고 | 부가 기능, 추가 통계 |
| **P3** | **AI 자율 탐색 영역** | **비통제** | 세부 레이아웃, 미세 인터랙션, 내부 구현, 시각 연출 |

### 3.1 Freedom Floor (v5에서 하드 하한 도입)

P3 / Freedom Zone 항목이 **3개 미만이면 스펙을 미완성으로 간주한다.**

근거: 모든 항목을 P0로 올리는 것이 실패 모드다. 통제 항목에는 상한을, 자유 항목에는 **하한**을 둔다. 자유도는 "남은 영역"이 아니라 **명시적으로 예약된 자산**이다.

**하드 하한 (v5 신설).** v4까지는 `PROJECT_SPEC.md`에 `freedom_floor: 0`을 쓰면 이 조항 전체가 꺼졌다. 즉 패키지의 존재 이유를 프로젝트가 한 줄로 무력화할 수 있었다. v5는 다음을 강제한다.

| 조건 | 처리 |
|---|---|
| `freedom_floor < 1` | **불가.** 자유 영역이 0인 스펙은 이 패키지의 대상이 아니다 |
| `1 ≤ freedom_floor < 3` | `freedom_floor_justification` 20자 이상 필수 |
| `freedom_floor ≥ 3` | 사유 불필요 |

자유도를 줄이는 것 자체는 금지가 아니다. **말없이 줄이는 것**이 금지다.

### 3.2 Control Ratio (신설, v3)

```
control_ratio = (P0 + P1 항목 수) / (P0 + P1 + Freedom Zone 항목 수)
```

기본 상한 **0.70**. 초과 시 경고하고, 어떤 항목을 P2·P3로 내릴 수 있는지 재검토한다.

기본 상한 **0.70**은 초과해도 완료를 차단하지 않는 **진단 지표(WARN)** 다. P0가 많은 안전 필수 프로젝트를 오탐으로 막지 않기 위해서다. 대신 하한(Freedom Floor)이 BLOCKER를 맡는다.

`control_ratio_cap` 자체를 0.85 초과로 부풀리면 경고한다. 지표를 무력화하는 방향의 자기 조정을 드러내기 위해서다.

> 0.70과 0.85는 **초기 기본값이며 실증되지 않았다.** 조정 사유는 `PROJECT_SPEC.md`에 기록한다.

## 5. Control Budget — 규칙을 늘리는 것에 대한 규칙

이 조항은 **2차 통제**다. 통제 계층 자체의 성장을 심사한다.

### 5.1 규칙의 2분류 (v3에서 수정)

| 유형 | 정의 | 추가 조건 |
|---|---|---|
| **사전규칙 (a priori)** | 위반 결과가 **비가역**인 규칙 | 실패 경험 **불필요**. 위해의 비가역성만 논증하면 즉시 채택 |
| **사후규칙 (a posteriori)** | 위반 결과가 품질 저하이며 **되돌릴 수 있는** 규칙 | 아래 4조건 **전부** 충족 시에만 채택 |

**사전규칙 예**: 개인정보 유출 금지, 과학적 사실 오류 금지, 데이터 영구 손실 금지, 학생 안전.
→ "한 번 당해 봐야 규칙을 만든다"는 사후 정당화가 성립하지 않는 영역이다. v2 이전 문서의 논리적 빈틈이 이 지점이었다.

> **예외 조항 설계 원칙 (v5).** 사전규칙을 조건부로 완화할 때, 그 조건은 **기계로 판정 가능해야 한다.** 판정되지 않는 예외는 예외가 아니라 규칙의 조용한 삭제다. 조건부 완화를 도입하면 같은 개정에서 `check_package.py`에 판정 규칙을 함께 넣는다.

**사후규칙 4조건**:
1. 실제 실패 경험이 있다
2. 재발 가능성이 높다
3. 실패 비용이 크다
4. 판정 기준이 명확하다 (사람 판정 / 기계 판정 중 무엇인지 명시)

### 5.2 최소화 대상

- 단순 취향
- 과도한 파일 구조 강제
- 구현 방식 과잉 지정
- 중복 지침
- 탐색을 막는 사소한 형식 규칙

### 5.3 규칙 삭제

**삭제는 추가와 동등한 개정 행위다.** 6개월간 한 번도 발화하지 않은 사후규칙은 삭제 후보로 검토한다.

## 6. Evaluation Engineering

코드보다 **좋은 결과의 기준**을 먼저 만든다.

| 코드 | 질문 | 측정 |
|---|---|---|
| E1 Correctness | 기능이 정확한가 | 자동 테스트 |
| E2 Reliability | 반복해도 안정적인가 | 회귀 스위트, 재시도 |
| E3 Usability | 처음 쓰는 사람이 스스로 쓰는가 | 사용자 관찰 |
| E4 Domain Quality | 그 분야 목적을 실제로 달성하는가 | 도메인 프로파일 참조 |
| E5 Product Quality | 다시 쓰고 싶은가 | 재사용 의사 |

### 6.1 증거 등급

| 등급 | 정의 |
|---|---|
| **V3** | 실제 사용자·실기기·실환경 관찰 |
| **V2** | 자동 테스트 또는 브라우저 실행 검증 |
| **V1** | 코드·문서 검토 |
| **V0** | 추정 |

규칙:
- P0는 **V2 이상** 필수
- 릴리스 범위 선언 시 **V2 증거로 V3를 대체 주장하지 않는다** (fixture·mock을 실환경 검증으로 확대 해석 금지)
- 증거 등급은 `STATE.md`와 노드 결과 문서에 명시한다

## 8. 과잉 엔지니어링 금지

다음 상황에서 구조를 복잡하게 만들지 않는다.

- 핵심 기능이 아직 검증되지 않았다
- 사용자 검증이 없다
- 기존 결함이 미해결이다
- 새 구조의 가치가 불명확하다

## 9. Definition of Done (2계층, v4에서 정합성 보강)

### 9.1 Machine-checked — `tools/check_package.py`가 판별

- [ ] `PROJECT_SPEC.md`가 존재하고 템플릿과 다르다
- [ ] P0 항목 ≥ 1
- [ ] Freedom Zone 항목 ≥ 3 (Freedom Floor)
- [ ] Freedom Floor 하드 하한 충족. 3 미만이면 사유 20자 이상 기재
- [ ] Control Ratio를 계산한다. 상한 초과는 **진단 WARN**이며 완료를 자동 차단하지 않는다
- [ ] `STATE.md` 스키마가 유효하고 status가 허용 집합에 속한다
- [ ] `STATE.md`의 증거 수치가 최신 노드 결과 문서와 일치한다 (드리프트 없음)
- [ ] custom graph의 **선행 노드** 결과 연속성을 진단한다 (누락·비PASS는 WARN)
- [ ] 현재 노드가 PASS가 아닌 상태에서 하류 노드에 **살아있는(live)** 결과가 없다 (revision 기준)
- [ ] 상류 노드를 수리했으면 그 하류 결과가 전부 폐기(`superseded` 또는 revision 상승)되었다
- [ ] 종료 노드 도달 여부가 상태에 표현되고 `active_node/terminal_node/status`가 정합하다
- [ ] custom graph의 모든 `FAIL ROUTE`가 비어 있지 않다
- [ ] `REPAIR/FALLBACK` 목적지가 실제 graph node와 정합하다
- [ ] 상태·노드 기록 시각은 timezone 포함 ISO datetime이다
- [ ] `STATE.revision`과 모든 `NODE_RESULT.revision`이 정합하다
- [ ] (science-education) 개인정보·자동채점 선언이 완비되어 있다

### 9.2 Human-checked — 사람이 판정

- [ ] 실제 화면에서 핵심 흐름 완주
- [ ] 회귀 없음
- [ ] 남은 Known Issue 기록
- [ ] 릴리스 범위와 미검증 범위 분리 선언
- [ ] 도메인 프로파일 체크리스트 통과

**두 계층 모두 통과해야 완료다.** 기계 통과만으로 완료를 선언하지 않는다.
